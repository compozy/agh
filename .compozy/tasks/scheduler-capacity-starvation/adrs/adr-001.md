# ADR-001: Hold Serial Backlog While Compatible Capacity Is Busy

## Status

Accepted

## Date

2026-07-15

## Context

Marketplace Task 11 real-scenario QA queued multiple runs for one owner pool. The pool intentionally reused one task-role session and AGH correctly enforced one active task-run lease per session. While that session processed earlier runs, `internal/scheduler` removed it from the eligible set because it was busy. Selection then treated the empty eligible set as worker absence, advanced the durable starvation ladder, and parked a later run as `needs_attention` after ten cycles.

The scheduler currently combines two independent questions in one boolean: whether a session structurally matches a run and whether that matching session is available now. Product policy is required because the correction can either preserve serial execution, add elastic workers, or combine both. The user explicitly selected serial waiting and rejected parallelism because it would add cost, conflicts, and operational complexity that are unnecessary now.

## Decision

AGH will classify matching capacity separately from momentary availability.

- A queued run is `available` when at least one structurally compatible active session is idle and not reserved by an earlier selection in the same cycle.
- A queued run is `capacity_waiting` when compatible capacity exists but is starting, prompting, holding an active run lease, or already reserved in the current cycle.
- A queued run is `unmatched` when no live session matches scope, workspace, coordination channel, owner, and required capabilities.
- A queued run is `indeterminate` when a possibly compatible live session cannot provide an authoritative capability projection.

`capacity_waiting` and `indeterminate` freeze any existing starvation budget. They do not request another worker, emit `task.run_starved`, or transition the run to `needs_attention`. `available` sessions continue to receive advisory wakes; an available session that repeatedly does not claim and an `unmatched` run continue through the existing bounded convergence ladder after `min_queued_age`.

AGH will not introduce elastic task-role workers, capacity thresholds, or new config keys in this change. `starved_run_count` keeps its public field name but counts queued runs with an active durable `task_run_starvation` episode rather than every run older than the raw age threshold.

## Alternatives Considered

### Alternative 1: Elastic Owner Pools

- **Description**: Start an additional task-role session whenever all compatible sessions are occupied.
- **Pros**: Higher throughput and shorter queues.
- **Cons**: Adds provider/token cost, concurrent workspace writes, claim races, pool limits, new lifecycle controls, and new configuration/status contracts.
- **Why rejected**: The user does not need parallelism now, and introducing it as a bug fix would silently change AGH's serial execution and cost model.

### Alternative 2: Hybrid Wait Then Expand

- **Description**: Hold serially for a configured duration, then start bounded additional workers.
- **Pros**: Preserves serial execution for short bursts while allowing later expansion.
- **Cons**: Requires a second durable saturation clock, capacity limits, cost policy, public diagnostics, config lifecycle, and conflict semantics.
- **Why rejected**: It combines the complexity of elastic pools with a new time policy that the current product does not require.

### Alternative 3: Increase Starvation Thresholds

- **Description**: Raise `min_queued_age` or `needs_attention_after` so busy serial queues have more time.
- **Pros**: Small code change.
- **Cons**: Delays real absence detection, remains workload-duration dependent, and still misclassifies busy capacity as missing.
- **Why rejected**: It patches the symptom without correcting the false state classification.

## Consequences

### Positive

- Serial owner pools drain in order without false intervention.
- Genuine worker absence and idle-worker refusal retain bounded recovery.
- No new provider cost, concurrency, config, migration, or public payload field is introduced.
- Public starvation pressure aligns with durable convergence state.
- Workspace, channel, owner, and capability isolation remain part of the capacity decision.

### Negative

- A slow compatible worker can keep later runs queued for a long time; session supervision and lease recovery, not starvation convergence, own that failure mode.
- Operators see capacity-held work through existing queued and active-claim counts rather than a new public `capacity_waiting_run_count`.
- A previously started starvation episode remains durable while capacity is temporarily busy and resumes if the run later becomes eligible or unmatched.

### Risks

- **False capacity hold**: A session from another workspace or channel could suppress convergence. Mitigation: structural matching applies scope, `workspace_id`, channel, owner, and capabilities before availability.
- **Capability projection failure stalls work**: Indeterminate sessions fail closed. Mitigation: emit structured `scheduler.session_context.error` and `scheduler.capacity_waiting` diagnostics; retry projection on every cycle.
- **Hidden regression in public status**: Raw queue age could continue to drive `starved_run_count`. Mitigation: count active `task_run_starvation` rows joined to claimable queued runs and cover HTTP/UDS/CLI parity.
- **Oversized owner files grow further**: `scheduler.go` and `scheduler_runtime.go` already exceed the production cap. Mitigation: extract selection/capacity and daemon session-projection/waker responsibilities before adding logic.

## Implementation Notes

- Preserve `task.Service.ClaimNextRun` as the sole claim authority; the scheduler only observes, wakes, sweeps, and escalates.
- Preserve one active lease per session and task-role session deduplication.
- Keep the existing `task_run_starvation` side table; do not add JSON metadata or a schema migration.
- Hard-cut the conflated `isEligibleSession` path into structural matching plus availability classification. Do not retain a compatibility wrapper.
- Hard-cut the raw-age public starvation query to active-episode semantics. Do not add a second status field or alias.
- Run a fresh isolated Northstar QA lab with one operator kickoff and mandatory clean teardown after focused verification.
