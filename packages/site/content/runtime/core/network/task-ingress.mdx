---
title: Task Ingress
description: How Network-originated task writes remain separate from execution participation, conversations, and task-run ownership.
---

Task ingress is a controlled write path from a validated Network peer into the task domain. It is
not the same thing as Live participation:

- participation decides whether an AGH execution joins a conversation and can receive bounded wakes
- ingress decides whether a peer may invoke a task mutation
- `task_runs` and claim tokens remain the only task ownership authority

## Gate checks

Before accepting an ingress write, AGH validates the workspace, peer, channel, request ID,
conversation metadata, current peer registration, and `task.write` capability. The actor identity
is derived from runtime-owned peer context; the request body cannot choose it.

Supported operations remain task-service calls:

| Action      | Runtime method       | Authority after ingress                                      |
| ----------- | -------------------- | ------------------------------------------------------------ |
| Create task | `CreateTaskFromPeer` | Creates durable intent only.                                 |
| Update task | `UpdateTaskFromPeer` | Uses normal task validation and actor policy.                |
| Cancel task | `CancelTaskFromPeer` | Uses the task service's cancellation transition.             |
| Enqueue run | `EnqueueRunFromPeer` | Resolves and persists that run's own participation snapshot. |

The ingress channel is correlation evidence. It is not copied into a legacy task channel field and
does not infer the new run's mode. A run without an explicit/profile/workspace Live request resolves
Local.

## Conversation and task authority

A Network message may request work, but its text cannot claim a run, extend a lease, mark a task
complete, or submit a review verdict. The receiving execution must use the session-bound task APIs.

`work_id` and `task_runs.id` are intentionally distinct. Ingress stores conversation correlation in
typed metadata without reusing Network lifecycle identity as task ownership identity.

## Thread promotion

Promoting a public-thread message creates a draft task and a durable origin link. It does not start
execution or force the task Live:

```bash
agh network threads promote \
  --channel builders \
  --thread thread_release_check_20260416 \
  --origin-message msg_thread_root \
  --title "Validate release migration gates" \
  -o json
```

Start the task separately and choose participation explicitly when needed:

```bash
agh task start task-123 \
  --network live \
  --network-channel-strategy run \
  -o json
```

## Rejection evidence

Rejected writes use deterministic reasons such as `capability_denied`, `peer_not_found`,
`task_ingress_unavailable`, `task_not_found`, `validation_failed`, `permission_denied`, and
`invalid_request`. The audit record includes the workspace, peer, channel, action, and request ID;
it never includes a raw claim token.
